1. 시스템 개요 (System Overview)
1.1 시스템 목적
Chatbot Generator Agent(이하 CGA)는 기업 운영자가 복잡한 코딩이나 프롬프트 엔지니어링 없이, 두 가지 입력 데이터만으로 고성능 엔터프라이즈 챗봇을 빌드·검증·배포하고 동적으로 진화시킬 수 있는 운영형 챗봇 팩토리 플랫폼이다.
핵심 입력 소스 (2가지)
① 질문 형태의 학습 문장 — 운영자가 원하는 의도(Intent) 개수(N개)를 지정하여 입력
② PDF 형태의 지식 문서 — 추출할 예상 질문 개수(M개)를 지정하여 업로드
1.2 설계 원칙
사용자 및 운영자가 Python 명령어 또는 Docker 스크립트를 직접 실행하지 않는다.
챗봇 생성·분석·배포는 시스템이 자동 또는 화면(UI) 기반으로 처리한다.
결과 확인은 DB/CLI가 아닌 화면과 API로 수행한다.
이상 상태는 시스템이 먼저 감지하여 운영 대시보드에 알람/경고로 표시한다.
설계는 내부 구조보다 실제 사용 흐름과 운영 흐름을 먼저 정의한다.

2. 전체 사용 및 운영 흐름 (User & Operations Flow)
2.1 단계 1 — 데이터 인입 및 LLM 초안 생성 (Build Phase)
운영자는 UI 화면에서 아래 두 가지 데이터를 입력한다. 이후의 모든 처리는 시스템이 자동으로 수행한다.
① 학습 문장 기반 의도 분류 흐름
운영자가 UI 화면에서 질문 형태의 학습 문장 더미를 입력하고, 원하는 의도 개수(N개)를 지정한다.
시스템 백엔드가 LLM을 호출하여 학습 문장들을 분석하고, 정확히 N개의 의도(Intent) 그룹으로 자동 분류한다.
분류된 N개의 의도 초안이 DB 임시 영역에 적재되고, 운영자 화면에 시각적으로 표시된다.
② PDF 지식 기반 예상 질문 역추출 흐름
운영자가 UI 화면에서 PDF 지식 문서를 업로드하고, 추출할 예상 질문 개수(M개)를 지정한다.
시스템 백엔드가 LLM을 통해 PDF 전문을 분석하고, 실제 사용자가 던질 법한 M개의 예상 질문을 역추출한다.
추출된 M개의 예상 질문 목록이 운영자 화면에 표시된다.
2.2 단계 2 — 운영자 편집 및 시나리오 매핑 (Human-in-the-Loop)
시스템이 생성한 초안을 운영자가 화면에서 검토하고 확정하는 단계이다. 모든 수정은 UI 화면에서 처리된다.
의도 조정: 유사 의도 합치기 / 불필요한 의도 삭제 / 누락 의도 추가
답변 매핑 (일반 사용자): 확정된 각 의도에 고정 답변 텍스트를 직접 입력
시나리오 구성 (고급 사용자): 시나리오 에디터를 통해 조건 분기 및 대화 흐름 블록 구성
배포 전 검증: 화면 내 테스트 채팅 창에서 사전 동작 확인
시나리오 에디터 — 고급 사용자 기능
단순한 질문-답변 매핑을 넘어, 조건 분기(If/Else)·메시지 카드·버튼·연속 대화 흐름을 블록 기반으로 구성
일반 운영자는 고정 답변 매핑으로 바로 챗봇 생성 가능 (시나리오 구성은 선택 사항)
2.3 단계 3 — 챗봇 빌드 및 배포 (Finalization)
운영자가 '완성' 버튼을 클릭하면 시스템이 조정된 의도·답변·시나리오 데이터를 규격화된 Chatbot Dynamic Template JSON으로 컴파일한다.
인프라 환경(공용 서버 / 자체 독립 서버)에 따라 시스템이 배포를 자동 처리한다. 운영자는 스크립트를 직접 실행하지 않는다.
배포 완료 후 등록된 메신저 채널(Web, 설치형 프로그램, 카카오톡)에서 즉시 서비스된다.
2.4 단계 4 — 무중단 런타임 및 동적 의도 확장 (Runtime Phase)
챗봇 서비스 운영 중 사전에 정의하지 않은 새로운 유형의 사용자 질문이 인입될 경우, 시스템이 자동으로 감지하고 처리한다.
런타임 엔진이 인입 질문과 기존 의도들 간의 유사도를 측정하여 설정 임계치 미달 시 '미정의 의도(Unknown Intent)'로 분류한다.
시스템 백엔드가 PDF RAG 컨텍스트를 탐색하여 현재 질문에 대한 임시 답변을 먼저 생성하여 사용자에게 제공한다. (서비스 무중단)
동시에, 해당 질문을 대표하는 신규 의도명과 최적화된 프롬프트를 LLM이 자동 생성하여 승인 대기 큐(PENDING_APPROVAL)에 적재한다.
운영 대시보드 화면에 [경고: 미정의 의도 감지 - 승인 대기 중] 알람이 즉시 발생한다.
운영자가 화면에서 생성된 신규 의도와 프롬프트를 검토 후 '승인' 버튼을 누르면, 서버 재시작 없이 런타임 템플릿에 동적 병합(Merge)되어 즉시 반영된다.
3. 4×4 하이브리드 NLU 및 답변 라우팅 매트릭스
본 시스템의 핵심 차별점이다. 모든 질문을 무거운 LLM 런타임으로 밀어 넣는 기성 솔루션의 고비용 구조와 달리, 4대 NLU 엔진과 4대 답변 유형의 매트릭스 조합을 통해 초고속 추론(Latency 최소화)과 운영 비용의 철저한 방어벽을 구축한다.

3.3 매트릭스 제어 원칙
운영자는 시나리오 에디터 화면을 통해 의도별로 NLU 엔진과 답변 유형의 조합 규칙을 직접 설정한다.
최적 비용 제어 전략 (권장)
일상적인 단순 반복 질문 약 80% → [자체개발 시멘틱 엔진] × [① 고정 답변 / ② 시멘틱 RAG] 조합으로 처리
위 조합만으로도 실제 운영 비용을 거의 0에 수렴시킬 수 있음
복합 판단이 필요한 약 20% → [③ LLM RAG] 또는 [④ 인터넷 검색] 동적 개방
결과: LLM 고비용 없이 기업 운영 환경에서 안정적·경제적인 챗봇 서비스 구현
4. 하이브리드 인프라 배포 아키텍처
모든 배포 제어는 관리자 화면 및 시스템 API 간 통신으로 처리된다. 운영자는 서버에 직접 접속하여 스크립트나 Docker 명령어를 실행하지 않는다.

4.2 배포 유형별 운영 흐름
[선택 A] 공용 공유형 서버 배포
운영자가 화면에서 의도·답변 설정을 완료하고 '공용 서버 배포'를 클릭한다.
시스템이 공용 서버의 Meta DB에 해당 챗봇의 고유 Tenant ID와 Template JSON을 적재하고 status를 ACTIVE로 변경한다.
Web / 설치형 프로그램: 공용 서버 API 엔드포인트에 접속하여 즉시 서비스 시작
카카오톡 채널: 공용 서버의 Webhook URL을 카카오 채널 관리자 센터에 등록하면 즉시 서비스
[선택 B] 자체 독립형 서버 배포 (자동 컨테이너 프로비저닝)
운영자가 화면에서 대상 서버 IP 및 인증 정보를 입력하고 '독립 컨테이너 배포'를 클릭한다.
시스템 백엔드가 Docker API를 원격으로 호출하여 챗봇 공통 런타임 이미지를 대상 서버에 Pull한다.
생성된 챗봇 전용 Template JSON과 PDF RAG 볼륨이 컨테이너 환경변수 및 마운트 경로에 자동 주입되며 컨테이너가 구동(Run)된다.
대상 서버의 리버스 프록시(Nginx)가 자동 설정되어 외부 API 엔드포인트가 노출된다.
Web, 설치형 프로그램, 카카오톡 Webhook이 해당 자체 서버 주소로 연결되어 서비스가 시작된다.

5.2 Fallback(대안 응답) 처리 정책
미정의 의도 인입 시 실시간 처리 (Pending 상태)
신규 의도가 시스템에 의해 생성되어 운영자 승인 대기(PENDING_APPROVAL) 상태일 때, 해당 질문을 던진 실제 사용자에게는 다음 Fallback 방식으로 즉시 대응한다.
RAG Fallback (기본 권장): 승인 전이지만 PDF RAG 검색으로 관련 문서 본문을 참조하여 LLM이 임시 답변을 생성하여 제공. 서비스 무중단 유지.
Buffer Fallback (선택): '처음 인입된 질문 유형으로, 정확한 답변을 위해 담당자 확인 중입니다.'라는 기본 안내를 제공.
연동 Tool API 오류 시 Fallback
챗봇이 참조하는 외부 API(Tool Connections)가 응답하지 않거나 오류를 반환할 때, 런타임 엔진은 전체 서비스를 중단하는 대신 표준 Fallback 메시지를 출력한다.
표준 Fallback 메시지 예시
"현재 연동 시스템 오류로 확인이 어렵습니다. 잠시 후 다시 시도해 주세요."
위 Fallback 메시지는 Template JSON의 tool_connections 규격 내 예외 처리 항목에 표준으로 내장됨
5.3 버전 관리 및 롤백
모든 챗봇 템플릿은 변경 시 자동으로 버전이 증가한다. (예: v1.0.0 → v1.0.1)
신규 배포 챗봇에서 이상이 감지되면 운영 화면에서 클릭 한 번으로 이전 안정 버전의 템플릿으로 즉시 원복(Rollback)한다.
모든 버전 이력은 Meta DB에 보관되며 운영자가 화면에서 비교 조회할 수 있다.

7. 시스템 내부 아키텍처 및 컴포넌트
각 컴포넌트는 느슨한 결합(Loose Coupling) 형태로 분리 설계하여, Generator 엔진에 장애가 발생하더라도 이미 배포된 챗봇의 런타임 서비스에는 영향을 주지 않도록 한다.

7.1 핵심 컴포넌트 역할 정의
컴포넌트
역할
Intent Analyzer
사용자의 학습 문장이나 PDF 입력을 분석하여 적합한 템플릿 카테고리 및 N개의 의도 그룹을 분류
Schema Validator
LLM이 생성한 프롬프트·설정 정보가 표준 JSON Schema를 만족하는지 배포 전 자동 검증. 미달 시 화면에 에러 알람 발생
Anomaly Detector
생성 실패, API 지연, 컨테이너 다운, 미정의 의도 인입 등을 실시간으로 감지하여 운영 대시보드에 알람 발생
Deployment Engine
운영자의 화면 클릭에 따라 Docker API를 원격 호출하여 컨테이너를 자동 프로비저닝하고 Template JSON을 주입
NLU Router
인입 질문을 의도별로 설정된 4대 NLU 엔진 중 지정 엔진으로 라우팅하여 유사도 점수 및 최종 의도 판정
Answer Router
NLU 판정 결과를 기반으로 4대 답변 유형(고정/시멘틱RAG/LLM RAG/인터넷) 중 설정된 방식으로 답변 생성·반환

8.2 전체를 엮는 통합 작업 방향
현재 개별적으로 개발 중인 핵심 기능들을 하나의 운영형 시스템으로 통합할 때의 핵심 원칙은 다음과 같다.
시나리오 에디터의 아웃풋 데이터 구조를 Template JSON의 scenario_config 영역 스펙에 맞추어 정합성을 확보한다.
자체 시멘틱 엔진의 의도 판정 결과(점수)와 NLU Router가 사용하는 인터페이스를 표준화하여 4대 엔진이 동일한 방식으로 결과를 반환하도록 설계한다.
Anomaly Detector가 모든 레이어(Generator, Runtime, 채널)에서 발생하는 이상 이벤트를 단일 알람 큐로 수렴하여 운영 대시보드에 통합 표시한다.
Dify 등 기성 솔루션이 해결하지 못한 '동적 의도 확장 승인 루프'와 '자체 시멘틱 엔진을 통한 비용 절감'을 화면(UI)으로 시각적으로 증명하는 것이 통합 작업의 최우선 목표이다.

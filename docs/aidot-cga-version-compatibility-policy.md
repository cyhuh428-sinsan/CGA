# Aidot-CGA 버전 호환 운영 정책서

## 목적

- Aidot가 계속 업그레이드되는 상황에서도 CGA와의 호환성을 안정적으로 유지하기 위한 운영 규칙을 정의한다.
- `최신본끼리 임시로 맞춘다`가 아니라 `버전 단위 계약`으로 호환 범위를 관리한다.
- Aidot 개발자와 CGA 개발자가 같은 기준으로 의사결정할 수 있도록 공통 규칙을 만든다.

## 배경 문제

- Aidot는 계속 기능이 추가되거나 내부 구조가 바뀔 수 있다.
- CGA는 Aidot와 `봇 다운로드/업로드/WebChat/운영 조회` 기준으로 호환되어야 한다.
- 그런데 Aidot가 기존 구조를 직접 바꿔버리면, CGA는 같은 시점에 같이 수정되지 않는 한 바로 깨질 수 있다.
- 따라서 Aidot와 CGA는 `제품 버전`이 아니라 `호환 계약 버전` 기준으로 맞춰야 한다.

## 핵심 원칙

### 1. 제품 버전과 계약 버전을 분리한다

- `제품 버전`:
  - Aidot `1.0`, `1.1`, `1.2`
  - CGA `1.0`, `1.1`, `1.2`
- `호환 계약 버전`:
  - `contract v1.0`
  - `contract v1.1`

의미:

- Aidot 제품 버전이 `1.2`가 되더라도, 외부 계약으로 `contract v1.0`을 계속 지원할 수 있어야 한다.
- CGA는 “현재 어떤 제품 버전과 호환”보다 “현재 어떤 계약 버전을 지원”하는지가 더 중요하다.

### 2. 기존 계약은 수정하지 않고 추가만 한다

- `contract v1.0`이 한번 확정되면 그 구조와 의미는 바꾸지 않는다.
- `contract v1.1`이 필요하면 `v1.0`을 수정하는 것이 아니라 `v1.1`을 추가한다.

허용:

- 새 필드 추가
- 새 API 추가
- 새 기능 추가
- 새 화면 추가
- 기존 기능을 최신 UI에서 숨김 처리

금지:

- 기존 필드 이름 변경
- 기존 필드 의미 변경
- 기존 응답 구조 변경
- 기존 저장 구조 삭제
- 기존 업로드 파일 포맷 변경
- 기존 WebChat/Simulator/Admin 계약 의미 변경

즉, `1.0은 얼리고`, `1.1은 옆에 추가`하는 방식으로 운영한다.

### 3. Aidot는 하위호환을 기본 원칙으로 한다

- Aidot는 새 버전이 올라가더라도 이전 계약 버전을 계속 처리할 수 있어야 한다.
- 최신 기능이 생겨도 `contract v1.0` 요청은 `v1.0 방식`으로 동작해야 한다.

예:

- Aidot `1.1`이 출시되더라도:
  - `contract v1.0` 업로드는 계속 수용
  - `contract v1.0` WebChat 흐름은 계속 동작
  - `contract v1.0` 운영 조회 구조도 계속 유지

### 4. CGA는 지원 계약 버전을 명시한다

- CGA는 “최신 Aidot 전체 지원”처럼 모호하게 말하면 안 된다.
- CGA는 아래처럼 분명하게 선언해야 한다.

예:

- 현재 지원: `contract v1.0`
- 부분 검증 중: `contract v1.1`
- 미지원: `contract v1.2`

### 5. 버전 협상 정보는 파일/API에 명시한다

- 봇 패키지 업로드/다운로드
- 버전 문서 업로드/다운로드
- WebChat 연결
- 운영 조회 API

위 영역에는 가능하면 `contract_version` 정보가 들어가야 한다.

예시:

- bot export JSON에 `contract_version`
- version document에 `contract_version`
- API 응답에 `supported_contract_versions`
- 업로드 요청 메타에 `target_contract_version`

## 권장 운영 모델

### 모델 A. 단일 최신 서버 + 하위호환 모드

가장 현실적인 기본안이다.

- Aidot 서버는 최신 버전 하나만 운영한다.
- 대신 내부에서 `contract v1.0`, `contract v1.1`을 분기 처리한다.

장점:

- 운영 서버가 하나라 관리가 단순하다.
- CGA는 같은 서버와 붙되 계약 버전만 맞추면 된다.

주의:

- 내부 구현은 바뀌어도 외부 계약은 보존돼야 한다.

### 모델 B. 계약 버전별 어댑터 계층

- Aidot 내부는 최신 구조로 유지한다.
- 외부 요청/응답만 계약 버전별 어댑터가 변환한다.

장점:

- 내부 구조 진화와 외부 호환을 분리할 수 있다.

주의:

- 어댑터 검증이 약하면 겉만 호환이고 실제 의미가 깨질 수 있다.

## 업로드/다운로드 정책

### 1. CGA 업로드 정책

- CGA는 자신이 지원하는 계약 버전까지만 업로드한다.
- 상위 계약 전용 기능은 기본적으로 자동 업로드하지 않는다.

권장 기본 동작:

- `contract v1.0` 업로드 모드
- `v1.1 이상 기능 포함 시 경고`
- 필요하면:
  - 제외 후 업로드
  - 차단 후 사용자 선택
  - 다운그레이드 변환

### 2. Aidot 업로드 수용 정책

- Aidot는 `contract_version`을 읽고 해당 계약 버전 규칙으로 파싱해야 한다.
- `v1.0` 업로드를 받았다고 해서 최신 구조로 덮어써 의미를 바꾸면 안 된다.

### 3. 다운로드 정책

- 다운로드도 `최신 형식 하나만` 내려주면 안 된다.
- 가능하면 계약 버전을 지정할 수 있거나, 최소한 현재 파일이 어떤 계약 버전인지 명시해야 한다.

### 4. 상위 버전 봇 처리 정책

- Aidot 제품 버전이 더 높더라도, CGA가 보장할 수 있는 기능은 최대한 유지한 채 수용하는 것이 기본 원칙이다.
- 판단 기준은 `제품 버전` 자체보다 `CGA가 그 기능 의미를 보장할 수 있느냐`다.

기본 원칙:

- CGA 지원 기능은 온전히 유지한다.
- CGA 미지원 상위 기능은 제거 또는 무시한다.
- 제거 또는 무시로 핵심 동작 의미가 깨지면 업로드를 차단한다.

권장 기본 동작:

- `경고 + 제거(또는 무시) 후 처리`
- 단, 핵심 기능 손실 시 `차단`

예:

- Aidot `1.2` 봇이라도 `contract v1.0` 범위만 사용하면 CGA 수용 가능
- Aidot `1.2` 전용 확장 기능이 있으면 해당 부분만 제거/무시
- 그 제거로 대화 흐름, 버전 문서 의미, WebChat 의미가 무너지면 수용하면 안 됨

## API/화면/저장 구조 정책

### 1. API 정책

- 기존 endpoint는 유지한다.
- 기존 request/response의 필수 필드는 유지한다.
- 새 기능은:
  - 새 endpoint 추가
  - 선택 필드 추가
  - 버전별 응답 확장
  중 하나로 처리한다.

### 2. 저장 구조 정책

- 최신 저장 구조를 도입하더라도, 이전 계약이 기대하는 의미는 유지해야 한다.
- 특히 `conversationHistory` 같은 핵심 구조는:
  - 기존 계약에서는 기존 의미 유지
  - 새 계약에서는 확장 필드 추가
  형태로 가야 한다.

### 3. 화면 정책

- 최신 UI에서 구버전 기능을 숨기는 것은 가능하다.
- 하지만 숨긴다고 해서 API/저장 구조/파일 포맷이 사라지면 안 된다.
- 필요하면 `고급 설정`, `레거시 모드`, `호환 업로드 모드`로 분리한다.

## CGA 관점의 적용 규칙

### 1. CGA 목표는 “Aidot 최신 전체 복제”가 아니다

- CGA 목표는 `지정한 계약 버전과의 안정적 호환`이다.
- 따라서 Aidot 새 기능이 생겨도 바로 모두 따라갈 필요는 없다.

### 2. CGA 업그레이드는 계약 버전 단위로 진행한다

예:

- 1차 목표: `contract v1.0` 100% 호환
- 2차 목표: `contract v1.1` 추가 지원

이렇게 해야 한 번 맞춘 `v1.0`을 유지한 채 확장할 수 있다.

### 3. CGA 내부 구조는 필요시 어댑터로 분리한다

- CGA 내부 모델과 Aidot 최신 내부 모델이 달라도 된다.
- 단, 외부 계약은 Aidot 계약 버전에 맞아야 한다.

### 4. 상위 버전 수용 방식

- CGA는 상위 제품 버전의 봇을 무조건 거부하지 않는다.
- 대신 아래 순서로 판단한다.

1. CGA가 보장하는 기능인지 확인
2. 미지원 기능을 제거/무시해도 핵심 의미가 유지되는지 확인
3. 유지되면 경고 후 수용
4. 유지되지 않으면 차단

이 원칙은 향후 `import/export 처리 정책`의 기본값으로 사용한다.

## Aidot 개발자와 합의해야 할 항목

### 반드시 합의할 것

1. `contract v1.0`을 어디까지로 볼 것인가
2. 제품 버전과 계약 버전을 분리할 것인가
3. 기존 계약은 수정 금지, 새 버전은 추가 방식으로 갈 것인가
4. 업로드/다운로드 파일에 `contract_version`을 넣을 것인가
5. WebChat/API/Admin 조회에 버전 협상 정보를 넣을 것인가
6. Aidot가 하위호환을 기본 원칙으로 보장할 것인가
7. CGA는 어떤 계약 버전부터 지원할 것인가

### 추천 합의 문장

아래 문장을 기준 합의안으로 제안할 수 있다.

> Aidot는 기존 계약 버전을 깨지 않고 유지한다.
> 새로운 기능이나 구조 변경은 기존 계약을 수정하지 않고 새 계약 버전으로 추가한다.
> CGA는 특정 계약 버전을 목표로 호환 작업을 수행하며, 지원하지 않는 상위 계약 기능은 자동으로 수용하지 않는다.

## 실무 적용 예시

### 예시 1. Aidot 1.0과 CGA가 호환된 상태

- Aidot `1.0` = `contract v1.0`
- CGA `1.0` = `contract v1.0` 지원

상태:

- 봇 업로드 가능
- 봇 다운로드 가능
- WebChat 가능
- 운영 조회 가능

### 예시 2. Aidot 1.1에서 기능 추가

- Aidot `1.1` 출시
- 새 기능은 `contract v1.1`로 추가
- 기존 `contract v1.0`은 유지

상태:

- CGA가 아직 `v1.1` 미지원이어도 `v1.0` 모드로 계속 동작
- CGA는 별도 일정으로 `v1.1` 지원 작업 진행

### 예시 3. CGA가 v1.0 모드로 업로드

- 사용자가 CGA에서 봇 업로드
- CGA는 `target_contract_version = v1.0`으로 업로드
- Aidot는 `v1.0` 규칙으로 수용
- `v1.1` 전용 기능은 자동 반영하지 않음

### 예시 4. Aidot 1.2 봇을 CGA가 가져오는 경우

- 원본 봇은 Aidot `1.2`에서 생성됨
- CGA는 먼저 `contract v1.0` 범위 기능만 해석
- CGA 미지원 상위 기능은 경고 후 제거 또는 무시
- 제거 후에도 핵심 의미가 유지되면 수용
- 제거 시 핵심 의미가 깨지면 업로드 차단

## 결론

- Aidot와 CGA의 호환은 `최신본 동기화` 방식으로 운영하면 계속 흔들린다.
- 가장 안전한 방식은 `버전 계약 기반 하위호환 정책`이다.
- 핵심은 아래 5가지다.

1. 제품 버전과 계약 버전을 분리한다.
2. 기존 계약은 수정하지 않는다.
3. 새 기능은 새 계약 버전으로 추가한다.
4. Aidot는 하위호환을 유지한다.
5. CGA는 지원 계약 버전만 명시적으로 처리한다.

이 문서는 Aidot 개발자와 CGA 개발자가 앞으로의 변경 기준을 맞추기 위한 합의 초안으로 사용한다.

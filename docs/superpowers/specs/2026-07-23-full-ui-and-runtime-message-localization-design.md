# CGA 전체 화면 및 런타임 기본 메시지 다국어화 설계

## 1. 목적

CGA Studio의 언어 선택이 일부 공통 화면에만 적용되는 현재 상태를 보완한다.
사용자에게 노출되는 화면 고정 문구를 한국어, 영어, 중국어(간체), 일본어,
베트남어, 프랑스어, 독일어로 제공하고, 기본 메시지도 호출 언어에 맞게
등록·조회·출력한다.

이번 작업은 화면 표시 문자열과 기본 메시지 선택 경계만 변경한다. 봇 UUID,
API 계약의 기존 필드, 대화 흐름, 의도 판정, 학습, Queue, 저장 및 삭제 동작은
변경하지 않는다.

## 2. 확정 범위

### 2.1 화면

- `apps/web`에서 사용자에게 노출되는 한국어 고정 문구 전체
- Admin 공통 하위 메뉴와 Admin 개별 화면
- API 관리 화면
- 봇 테스트 화면
- 나머지 Studio 화면
- 로그인, 회원가입, 사용자 언어 설정과 기존 다국어 화면의 누락 문구

DB에서 읽는 봇 이름, API 이름, 의도명, 사용자명과 사용자가 직접 등록한 업무
데이터는 자동 번역하지 않는다. API가 반환한 오류 원문도 임의 번역하지 않는다.

### 2.2 기본 메시지

- `admin_default_messages`의 기존
  `(organization_id, message_key, language)` 고유 구조 유지
- 각 메시지 키에 대해 7개 지원 언어 레코드 보장
- Admin 화면에서 언어별 메시지 조회·수정
- 런타임에서 요청 언어와 봇 언어를 기준으로 메시지 선택

## 3. 화면 다국어 구조

현재 `LanguageProvider`의 언어 상태를 화면 다국어화의 단일 기준으로 사용한다.
카탈로그는 하나의 거대 파일로 합치지 않고 기능 경계별로 분리한다.

- Admin 메뉴 및 공통 레이아웃
- Admin 개별 화면
- API 관리
- 봇 테스트
- Studio 기능 화면

각 카탈로그는 동일한 7개 언어 키를 제공해야 한다.

- `ko`
- `en`
- `zh-CN`
- `ja`
- `vi`
- `fr`
- `de`

화면 컴포넌트의 고정 문구는 현재 언어 카탈로그에서 가져온다. 현재 언어에
해당 키가 없으면 한국어 카탈로그를 최종 UI fallback으로 사용한다.

브라우저의 API 호출 방식은 기존과 동일하게 same-origin `/api/v1` 경로를
사용한다. 내부 API 주소는 Next.js BFF에서만 해석한다.

## 4. 기본 메시지 저장

배포 또는 Admin 기본 메시지 최초 조회 시 각 조직에 필요한 메시지 키와 7개
언어 조합을 보장한다.

- 기존 한국어 레코드는 유지한다.
- 이미 존재하는 사용자 수정 메시지는 덮어쓰지 않는다.
- 누락된 언어 레코드만 시스템 기본 번역본으로 추가한다.
- seed 및 보정 작업은 반복 실행해도 기존 사용자 값을 바꾸지 않아야 한다.
- 메시지 키와 언어는 레코드 식별 속성이므로 일반 수정 화면에서 변경하지 않는다.
- 메시지 내용, 설명, 사용 여부만 수정할 수 있다.

## 5. 런타임 언어 결정

요청별 언어 결정 순서는 다음과 같다.

1. 요청 JSON의 `language`
2. HTTP `Accept-Language` 헤더
3. 봇 설정 언어
4. 한국어

지원하지 않는 값과 빈 값은 무시하고 다음 후보를 사용한다.
지역 코드는 지원 언어로 정규화한다.

- `en-US`, `en-GB` → `en`
- `ja-JP` → `ja`
- `vi-VN` → `vi`
- `fr-FR` → `fr`
- `de-DE` → `de`
- `zh-CN` 및 중국어 간체 별칭 → `zh-CN`
- `ko-KR` → `ko`

## 6. 런타임 메시지 fallback

결정된 언어의 메시지가 없거나 비활성 상태일 때 다음 순서로 조회한다.

1. 결정된 요청 언어의 활성 메시지
2. 봇 언어의 활성 메시지
3. 한국어 활성 메시지
4. 코드에 포함된 한국어 안전 기본값

같은 언어가 중복 후보로 들어오면 한 번만 조회한다. 메시지 선택 실패가 대화
처리를 중단해서는 안 된다.

## 7. API 영향

기존 채널 요청은 그대로 동작해야 한다. `language`는 선택 필드로 추가한다.
필드가 없으면 기존 요청과 동일하게 처리하면서 봇 언어를 사용한다.

지원 대상:

- 일반 채널 연결 및 채팅방 생성
- 채널 메시지 처리
- 봇 테스트/시뮬레이터 호출
- Kakao, Webchat, Teams 등 채널 요청에서 확인 가능한 언어 값

각 채널 고유 payload에서 명시 언어를 추출할 수 없는 경우 HTTP 헤더와 봇
언어를 사용한다. 기존 채널 payload 해석 규칙은 변경하지 않는다.

## 8. 오류 처리

- 잘못된 언어 값은 요청 자체를 실패시키지 않고 다음 fallback 후보로 이동한다.
- Admin 메시지 수정 시 존재하지 않는 언어 코드를 새로 허용하지 않는다.
- API 오류 상세와 사용자가 저장한 메시지는 화면 언어 변경으로 자동 번역하지 않는다.
- 번역 키 누락은 계약 테스트에서 실패시킨다.
- 화면이 렌더링되는 마지막 방어선은 한국어 카탈로그다.

## 9. 구현 단위

1. Admin 공통 메뉴와 Admin 화면
2. API 관리 화면
3. 봇 테스트 및 나머지 Studio 화면
4. 전체 사용자 노출 고정 한국어 잔여 정리
5. 7개 언어 기본 메시지 생성·관리
6. 요청 언어 정규화와 런타임 메시지 선택
7. 전체 회귀 및 브라우저 검증

각 단위는 RED → GREEN → 관련 테스트 → Next.js 빌드 또는 API 회귀 테스트 →
커밋 순서로 처리한다.

## 10. 테스트 및 완료 조건

### 자동 테스트

- 모든 화면 카탈로그에 7개 언어 키 존재
- 사용자 노출 고정 한국어 문구 잔여 검사
- 기존 CSV 헤더와 사용자 업무 데이터 비번역 확인
- 기존 한국어 기본 메시지 보존
- 누락 언어 레코드만 생성
- 사용자 수정 메시지 보존
- JSON `language` 우선
- `Accept-Language` 차순위
- 봇 언어 fallback
- 한국어 DB 메시지 fallback
- 코드 안전 기본값 fallback
- 지원하지 않는 언어 무시
- 기존 언어 없는 요청의 동작 호환

### 빌드 및 실행 검증

- API 관련 전체 테스트 통과
- Next.js 프로덕션 빌드와 타입 검사 통과
- 1920×1080 기준 주요 화면의 7개 언어 전환 확인
- 로그인된 브라우저에서 Admin, API 관리, 봇 테스트, 기본 메시지 화면 확인
- Browser Network에서 내부 API 주소나 localhost 직접 호출이 없음
- 기존 한국어 봇과 기존 기본 메시지 값 보존 확인

## 11. 비범위

- 사용자 업무 데이터 자동 번역
- LLM을 이용한 실시간 화면 번역
- 기존 대화 흐름·의도 판정·학습·Queue 구조 변경
- 봇 언어의 사후 변경 허용
- Aidot 소스 또는 운영 데이터 변경
- 이번 기능 브랜치의 즉시 `main` 병합 및 운영 배포

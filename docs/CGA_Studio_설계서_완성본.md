# CGA Studio 설계서 완성본

작성 기준: 신산님 제공 CGA 개념 문서, `CGA 설계서.docx`, `CGA_Studio_화면설계서_v2.0.docx`, 지금까지의 대화 결정, Aidot 기반 재구성 원칙  
작성 상태: 화면 설계 검토용 초안  
중요 제한: Aidot 수정 금지. CGA 작업은 Aidot 구조/기능/체계를 그대로 유지하고 화면 구성만 재배치한다.

## 1. 제품 정의

CGA Studio는 Aidot에 이미 구현된 봇 생성, 설정, 구성, 의도, 학습문장, PDF/RAG, 학습, 시뮬레이터, 평가, 분석, 배포 기능을 사용자가 봇을 제작하는 실제 순서에 맞게 재구성한 Studio 화면이다.

CGA는 챗봇 메신저가 아니다. CGA는 봇 서버, 봇 클라이언트 배포 대상, 운영 설정을 구성하고 관리하는 제작 플랫폼이다.

Aidot는 기능 중심 화면이고, CGA Studio는 작업 순서 중심 화면이다.

CGA Studio의 핵심은 Aidot 기능을 새로 만드는 것이 아니라, 사용자가 “다음에 무엇을 해야 하는지” 알 수 있도록 Aidot 기능을 제작 순서대로 다시 배치하는 것이다.

## 2. 절대 원칙

1. Aidot의 코드, 문서, 설정, API는 수정하지 않는다.
2. Aidot의 구조, 기능, API, 런타임 변수, 시뮬레이터, webchat, 채널 체계는 그대로 유지한다.
3. CGA에서 새 기능 개발은 기본 금지다.
4. 새 기능이 필요하면 반드시 `새로운 기능 개발 요청`이라고 명시하고 신산님 승인 후 진행한다.
5. CGA의 핵심 개발 대상은 기능 자체가 아니라 화면 구성과 작업 흐름이다.
6. 화면부터 설계하고, 기능 구현은 승인된 화면 단위로만 진행한다.
7. CGA Studio는 멀티랭귀지를 기본으로 한다. Aidot는 한국어 기준이지만, CGA Studio 화면 라벨과 사용자 흐름은 영어 기본으로 설계한다.
8. 카카오톡 채널은 한국어 버전에만 구현한다. 다른 언어권 메신저 포팅은 카카오톡 구조를 참고해 별도 구현한다.

## 3. 개발 범위 판단

CGA Studio는 새 시스템 개발이 아니라 Aidot 기반 Workflow Shell이다.

권장 범위는 아래와 같다.

| 구분 | 방향 |
| --- | --- |
| 재사용 대상 | Aidot 구조, API, 데이터 모델, 봇 설정, 의도, 학습문장, 사전, 개체, 대화 설계, 답변, 시뮬레이터, 평가, 분석, 배포, 채널 |
| CGA 신규 대상 | 화면 순서, 메뉴 구조, 초보/고급 노출 방식, 단계별 상태 패널, 승인 흐름 UI |
| 금지 대상 | Aidot API 변경, 런타임 구조 변경, webchat 호환성 변경, 데이터 모델 임의 변경, 새 기능 임의 개발 |

기준 비율은 `Aidot 기능 재사용 80~90%`, `CGA 화면 재구성 10~20%`로 본다.

## 3.1 Aidot 기능 화면 전체 보존 원칙

CGA는 Aidot 기능 화면을 빼거나 제외하는 프로젝트가 아니다.

원칙:

- Aidot에 있는 기능 화면은 모두 필요하다.
- CGA는 기능을 제거하지 않고 봇 제작/운영 흐름에 맞게 재배치한다.
- 초보자에게 처음부터 복잡한 기능명을 강하게 노출하지 않을 수는 있지만, 해당 기능 화면 자체를 없애지는 않는다.
- 초보자 경로 밖에 있는 기능은 단계별 Advanced, Detail, Operate, Improve 영역에 배치한다.
- 기능 화면이 보이지 않는다면 “제외”가 아니라 “아직 매핑되지 않음”으로 보고 매핑표를 보완한다.

## 3.2 공동 작업 플랫폼 원칙

CGA의 기본 목표는 한 사람이 1~2일 안에 봇 하나를 만들 수 있는 빠른 제작 플랫폼이다. 동시에 봇 규모가 크거나 운영 조직이 있는 경우 여러 명이 하나의 봇을 공동 제작할 수 있어야 한다.

따라서 사용자, 로그인, 역할, 권한, 작업 배정, 검수, 편집 잠금, 변경 이력은 Public Core 단계부터 고려한다.

초기 화면은 1인 제작 속도를 방해하지 않아야 한다. 협업 기능은 필요할 때 확장되는 구조로 두되, 내부 상태 모델은 처음부터 사용자/역할/작업 배정/검수/이력을 지원할 수 있어야 한다.

## 3.3 그룹 중심 SaaS 운영 원칙

CGA는 개별 설치형 데스크톱 도구가 아니라 서버에 설치해 서비스하는 SaaS 구조를 기본으로 한다.

오픈소스 사용자는 각자 서버에 CGA를 설치할 수 있지만, 설치 후 사용 방식은 동일하다. 사용자는 브라우저로 CGA Studio 서버에 접속하고, 그룹 단위로 봇과 API를 관리한다.

원칙:

- 모든 관리 기준은 시스템 전체가 아니라 그룹이다.
- 봇은 그룹이 관리한다.
- API 답변도 그룹이 관리한다.
- 그룹별 사용자 권한을 설정한다.
- 동일 그룹에 속한 사용자는 그룹이 관리하는 봇에 접근할 수 있다.
- 화면/기능 접근은 그룹 멤버십, 그룹 내 사용자 역할, 그룹별 scope로 결정한다.
- 서버 운영자는 인프라를 관리하지만, 봇/API/사용자 권한의 업무 기준은 그룹이다.
- 폐쇄망에서도 CGA는 SaaS 구조로 설치해 사용한다.
- 개인 사용자는 WSL 또는 Docker 컨테이너로 CGA 서버를 띄우고 브라우저로 접속해 사용할 수 있다.
- 클라우드, 사내 서버, 폐쇄망 서버, 개인 PC의 WSL 컨테이너는 배포 위치만 다르며 제품 사용 구조는 동일하다.

### 3.3.1 가입신청과 관리자 권한 원칙

- 모든 사용자는 가입 시 자기 그룹으로 먼저 가입된다.
- 사용자는 다른 그룹에 가입신청을 할 수 있다.
- 특정 그룹에 가입되면 그 그룹의 사용자 권한으로 봇/API/화면 접근이 결정된다.
- 그룹의 사용자가 모두 없어지면 해당 그룹은 삭제한다.
- 그룹은 언제든지 다른 그룹으로 이동하거나 새로 생성할 수 있다.
- 그룹 생성은 관리자 권한을 가진 사람만 가능하다.
- 시스템 전체에는 기본 사용자 `admin`을 둔다.
- `admin`은 삭제할 수 없는 기본 사용자다.
- 관리자 권한 요청은 `admin` 사용자가 승인한다.
- 각 그룹에는 그룹 관리자 1명이 있어야 한다.
- 그룹 관리자는 해당 그룹 안에서 모든 권한을 가진다.
- 언어 설정은 사용자별로 관리한다.
- 같은 그룹 사용자라도 각자 다른 UI 언어로 CGA Studio를 사용할 수 있다.
- 다양한 언어 사용자가 하나의 그룹에서 같은 봇을 공동 작업할 수 있어야 한다.
- 에러 메시지와 운영 알림은 `user.locale` 기준으로 표시한다.
- 봇 기본 언어와 사용자 UI 언어는 분리한다.

## 4. 전체 화면 구조

CGA Studio의 기본 화면은 기능 메뉴가 아니라 제작 진행판이다.

`CGA_Studio_화면설계서_v2.0.docx` 기준으로, 사용자에게 직접 보이는 기본 제작 단계는 6단계로 단순화한다.

```text
CGA Studio 기본 노출 단계
├─ 01 봇 생성
├─ 02 봇 구성
├─ 03 상세 설정
├─ 04 빌드
├─ 05 테스트
└─ 06 운영
```

다만 내부 설계와 고급 사용자 화면에서는 Aidot 기능 매핑을 명확히 하기 위해 아래 세부 단계를 유지한다.

```text
CGA Studio 내부 세부 단계
├─ Create
├─ Setup
├─ Configure
├─ Review
├─ Edit
├─ Train
├─ Test
├─ Improve
└─ Deploy
```

상단에는 현재 봇, 버전, 언어, 상태, 저장/테스트/배포 버튼을 둔다.  
왼쪽에는 제작 단계를 둔다.  
중앙에는 현재 단계 작업 화면을 둔다.  
오른쪽에는 현재 봇의 완성도, 누락 항목, Aidot 호환 상태, 다음 작업을 둔다.

```text
CGA Studio
┌──────────────────────────────────────────────┐
│ Bot / Version / Language / Status / Actions  │
├───────────────┬───────────────────┬──────────┤
│ 제작 단계      │ 현재 작업 화면      │ 상태 패널 │
│               │                   │          │
│ 01 봇 생성     │                   │          │
│ 02 봇 구성     │                   │          │
│ 03 상세 설정   │                   │          │
│ 04 빌드       │                   │          │
│ 05 테스트     │                   │          │
│ 06 운영       │                   │          │
└───────────────┴───────────────────┴──────────┘
```

### 4.1 글로벌 레이아웃 규칙

모든 주요 화면은 4영역 구조를 공유한다.

| 영역 | 역할 | 표시 정보 |
| --- | --- | --- |
| TopBar | 현재 작업 컨텍스트 | 봇명, 버전, 저장 상태, 임시저장, 계속 버튼 |
| Step Rail | 제작 단계 이동 | 01 봇 생성, 02 봇 구성, 03 상세 설정, 04 빌드, 05 테스트, 06 운영 |
| Main Workspace | 현재 단계의 실제 작업 | 입력 폼, 검수 목록, 편집 화면, 시뮬레이터 등 |
| Status Panel | 준비 상태와 다음 작업 | 필수 누락, LLM 연결 상태, 검증 결과, 다음 단계 안내 |

화면 설계 원칙:

- 사용자는 기능 메뉴가 아니라 다음 작업을 먼저 본다.
- Aidot 기능 화면은 모두 유지한다. 초보자 화면에서는 작업 언어로 안내하고, 세부 기능 화면은 단계별 고급/운영 영역에 배치한다.
- 모든 단계는 완료 조건을 가진다.
- 완료 조건을 만족하지 못하면 다음 단계 이동은 안내 상태로 둔다.

### 4.2 사용자 노출 6단계와 내부 세부 단계 매핑

| 사용자 노출 단계 | 내부 세부 단계 | 완료 조건 |
| --- | --- | --- |
| 01 봇 생성 | Create / Setup | 봇명 저장, 기본 언어와 채널 기본값 설정 |
| 02 봇 구성 | Configure / Review | 의도 1개 이상 완료, 후보 검수 완료 |
| 03 상세 설정 | Edit | 저장 완료. 단, 초보 사용자는 선택적으로 건너뛸 수 있음 |
| 04 빌드 | Train / Deploy 준비 | 학습 또는 빌드 처리 성공, 필수 누락 없음 |
| 05 테스트 | Test | 시뮬레이터 테스트 통과 또는 미해결 이슈 확인 |
| 06 운영 | Deploy / Improve / Operate | 운영 반영 완료, 채널 상태 확인 |

이 매핑은 화면을 단순하게 유지하기 위한 것이다. Aidot 내부 기능을 줄이거나 변경한다는 의미가 아니다.

## 5. 사용자 유형

### 5.1 초보 사용자

목표: 클릭 몇 번으로 기본 봇을 만든다.

초보자 화면에서는 작업 언어로 풀어 쓰고, 원래 Aidot 기능명은 해당 단계의 세부/고급 화면에서 함께 제공하는 용어:

- Intent
- Entity
- Dictionary
- Flow graph
- API Tool
- Runtime variable
- ML / Semantic / RAG 내부 구조

초보자 화면 표현:

- 봇 만들기
- 질문 예시 넣기
- 문서 넣기
- 자동 초안 만들기
- 후보 확인하기
- 답변 고치기
- 테스트하기
- 배포하기

### 5.2 고급 사용자

목표: Aidot 기능을 활용해 세밀한 봇을 만든다.

고급 사용자는 각 단계 안의 Advanced 영역에서 Aidot 기능을 직접 다룬다.

## 6. 단계별 화면 설계

### 6.1 Create

목적: 봇을 생성한다.

Aidot 기준 기능:

- 봇 생성
- 봇 유형
- 봇 이름
- 언어
- 프로필
- 기본 설명
- 버전 이름

CGA 화면에서는 복잡한 엔진 선택을 먼저 크게 보여주지 않는다. 봇 제작 시작에 필요한 최소 정보만 받는다.

주요 항목:

- Bot Name
- Description
- Default Language
- Bot Type
- Version Name

### 6.1.1 Create 단계 구조 결정 원칙

Create Bot은 단순 생성 화면이 아니라 봇 구조에 영향을 주는 선택을 확정하는 단계다.

Create Bot에서 결정해야 하는 항목:

- LLM을 봇 구성에 사용할지 여부
- 구성 입력 방식: 학습문장, PDF, 학습문장 + PDF
- PDF 기반 Q&A 의도 생성을 허용할지 여부
- 오케스트레이터 모드: 기존 오케스트레이터 연결, 신규 컨테이너 구축, 나중에 결정
- Bot Server 위치: 오케스트레이터 서버와 동일, 별도 서버, 나중에 결정
- 기본 채널: Web, 설치형 메신저, Kakao KR

이후 단계에서 변경 가능한 항목:

- LLM Provider
- LLM Model
- LLM Base URL
- 프롬프트 템플릿 세부값
- 실행/비용 관련 옵션

기준:

- 전체 봇 구조에 영향을 주는 선택은 Create Bot에서만 설정한다.
- 이후 단계에서 구조 변경이 필요하면 Create Bot으로 돌아가 변경한다.
- LLM 모델 변경처럼 전체 구조를 깨지 않는 선택은 필요한 단계에서 조정 가능하다.


### 6.1.2 Aidot 학습 이후 변경 불가 항목

원칙:

- Aidot에서 학습 이후 변경이 불가능하거나 변경하면 봇 구조가 깨지는 항목은 모두 Create Bot에서 설정한다.
- 이후 단계에서는 이 구조를 전제로 편집, 학습, 테스트, 운영만 진행한다.
- 구조 변경이 필요하면 해당 단계에서 임의 변경하지 않고 Create Bot으로 돌아가 수정한다.

Create Bot에서 잠그는 항목:

- LLM 사용 여부
- 구성 입력 방식: 학습문장, PDF, 학습문장 + PDF
- PDF 기반 Q&A 의도 생성 허용 여부
- 기본 언어
- 기본 채널 구성
- 오케스트레이터 모드
- Bot Server 위치

학습 이후에도 변경 가능한 항목:

- LLM Provider
- LLM Model
- LLM Base URL
- 프롬프트 템플릿 세부값
- 비용 제한, timeout 같은 실행 옵션

기준:

- 봇 구조를 바꾸는 설정은 Create Bot
- 실행 옵션을 바꾸는 설정은 해당 단계에서 조정 가능

### 6.1.3 화면 정책

CGA Studio는 잠금 항목과 실행 옵션을 화면에서 명확히 분리해 보여준다.

- `Locked in Create Bot`: Aidot 학습 이후 변경하면 안 되는 구조 설정
- `Runtime-adjustable later`: 학습 이후에도 봇 구조를 깨지 않고 조정 가능한 실행 옵션

이 구분은 사용자가 나중에 구조를 임의로 바꾸는 것을 막기 위한 운영 안전 장치다.


### 6.2 Setup

목적: 기본 파라미터를 설정한다.

Aidot 기준 기능:

- 언어 설정
- 답변 방식
- LLM Provider
- LLM Model
- LLM Base URL
- 채널 기본값

CGA 기준:

- Aidot는 ML / Semantic / LLM을 모두 선택 가능하다.
- CGA의 봇 구성 흐름은 LLM 방식만 우선 노출한다.
- 단, Aidot 내부 기능은 제거하지 않는다.
- CGA 화면에서 봇 구성 흐름만 LLM 기준으로 제한 노출한다.

### 6.3 Configure

목적: 봇의 초기 의도 구성을 만든다. CGA에서 가장 중요한 화면이다.

구성 방식은 두 가지다.

#### A. 학습문장 입력 → 의도 분류

- 사용자가 학습문장을 입력하거나 파일로 넣는다.
- 원하는 의도 개수를 지정한다.
- 프롬프트와 학습문장을 구성한다.
- LLM 엔진이 연결되어 있으면 시스템이 직접 LLM 호출한다.
- LLM 엔진이 연결되어 있지 않아도 가능해야 한다.
- 이 경우 CGA는 프롬프트와 학습문장 파일을 만들어 사용자가 외부 LLM에 전달할 수 있게 한다.
- 사용자가 외부 LLM 답변을 가져와 입력하면 CGA가 의도 구성을 반영한다.

주의: LLM 미연결 상태에서 외부 LLM용 프롬프트/파일 생성과 결과 붙여넣기 화면은 새 기능처럼 보일 수 있으므로, Aidot에 이미 대응 구조가 있는지 확인 후 구현한다. 없으면 `새로운 기능 개발 요청`으로 분리한다.

#### B. PDF 입력 → 질문/답변 의도 생성

- 사용자가 PDF를 입력한다.
- PDF에서 예상 질문과 답변으로 이루어진 의도 후보를 만든다.
- 이 방식은 LLM이 연결된 경우에만 가능하다.
- LLM 연결이 없으면 이 화면은 비활성 또는 안내 상태로 둔다.

## 7. LLM 연결 상태와 수동 Handoff 규칙

CGA Studio의 봇 구성 단계는 LLM 전용으로 노출한다. Aidot 내부의 ML / Semantic 기능은 제거하지 않지만, CGA의 초보 제작 흐름에서는 사용하지 않는다.

### 7.1 LLM 연결 상태 표시

| 상태 | 표시 | 동작 |
| --- | --- | --- |
| LLM 연결됨 | 녹색 칩 `LLM Connected` | 학습문장 경로와 PDF 경로 모두 자동 실행 가능 |
| LLM 미연결: 학습문장 경로 | 황색 칩 `LLM Not Connected` | 수동 LLM Handoff 버튼 표시, 자동 분류 버튼 비활성화 |
| LLM 미연결: PDF 경로 | 빨간 칩 `LLM Required` | PDF 파일 저장은 가능, Q&A 의도 생성 버튼 비활성화 |

### 7.2 수동 LLM Handoff

수동 LLM Handoff는 LLM이 연결되지 않은 환경에서도 학습문장 기반 의도 구성을 진행하기 위한 흐름이다.

기본 흐름:

1. 프롬프트와 학습문장이 담긴 `.txt` 파일을 내보낸다.
2. 사용자가 ChatGPT, Claude, Gemini 등 외부 LLM에 내용을 붙여넣는다.
3. 외부 LLM이 반환한 의도 분류 결과를 복사한다.
4. CGA Studio에 결과를 붙여넣거나 파일로 가져온다.
5. CGA가 결과를 검증한 뒤 의도 후보를 생성한다.

파일 규칙:

| 항목 | 형식 | 설명 |
| --- | --- | --- |
| 내보내기 파일 | Plain Text `.txt` | 지시 프롬프트와 학습문장 목록 포함 |
| 가져오기 파일 | JSON `.json` 또는 Plain Text | 의도명과 학습문장 목록 포함 |
| 기본 JSON 구조 | `{ intents: [{ name, sample_utterances[] }] }` | CGA가 파싱해 의도 후보 목록으로 반영 |

주의:

- 이 흐름은 새 기능처럼 보일 수 있으므로 Aidot에 대응 가능한 데이터 반영 구조가 있는지 확인해야 한다.
- 대응 구조가 없으면 즉시 구현하지 않고 `새로운 기능 개발 요청`으로 신산님 승인 후 진행한다.
- 중복된 `intent_name` 자동 병합 같은 동작도 기존 Aidot 구조로 가능한지 확인 전에는 구현하지 않는다.

## 8. 운영 화면 보완

운영 화면은 Aidot 운영 기능을 재배치해 보여준다.

표시 영역:

| 영역 | 표시 정보 | 알람 조건 |
| --- | --- | --- |
| 채널 상태 | Web / 설치형 / 카카오톡 연결 상태와 응답 시간 | 응답 실패 3회 이상 |
| 대화량 현황 | 시간대별 대화 건수, 의도별 빈도 순위 | 이상 급증 또는 급감 |
| 미정의 의도 알람 | 임계치 미달 의도 감지 목록, 승인 대기 큐 | 신규 미정의 의도 감지 |
| 컨테이너 상태 | 자체 서버 Docker 헬스체크 결과 | 컨테이너 다운 |
| LLM 비용 현황 | LLM 호출 건수와 토큰 비용 집계 | 설정 임계치 초과 |

주의:

- 운영 대시보드는 Aidot에 이미 있는 운영/분석 정보를 재배치하는 범위에서 먼저 설계한다.
- `동적 의도 확장 승인`은 새 기능 가능성이 높다. Aidot 기존 기능만으로 가능한지 확인 전에는 구현하지 않는다.
- 자동 신규 의도 생성, 승인 대기 큐, 자동 재학습 연결은 모두 `새로운 기능 개발 요청` 후보로 분리한다.

## 10. 오픈 코어 및 상용 모듈 분리 전략

CGA는 개발 완료 후 GitHub public 공개를 전제로 한다. 따라서 공개해도 되는 영역과 상용 가치가 큰 영역을 처음부터 분리한다.

핵심 방향:

- 공개 저장소만으로도 기본 봇 제작과 운영 흐름은 가능해야 한다.
- 상용 가치가 큰 고급 자동화, 운영 고도화, 라이선스 통제 기능은 별도 모듈로 분리한다.
- 공개 코드 안에 단순 잠금장치를 넣는 방식은 우회 가능성이 높으므로 핵심 보호 전략으로 삼지 않는다.
- 보호 대상은 “코드 잠금”이 아니라 “상용 가치가 큰 기능 모듈”이다.

### 10.1 Public Core

Public Core는 GitHub public 저장소에 공개 가능한 영역이다.

| 영역 | 포함 내용 | 원칙 |
| --- | --- | --- |
| CGA Orchestrator Core | Aidot 호환 API 계약, 기본 봇 생성/설정/배포 흐름 | 누구나 설치 가능 |
| CGA Studio Basic | 6단계 화면, 기본 입력/검수/편집 UI | 화면 흐름 공개 |
| Aidot-Compatible Runtime Contract | webchat, AM/채널, 변수/함수, 시뮬레이터 계약 | Aidot와 호환 유지 |
| Basic Builder Flow | 학습문장 입력, 기본 의도 검수, 답변 편집, 테스트 | 기본 봇 제작 가능 |
| Basic Deployment | Web 클라이언트 연결, 기본 Bot Server 배포 안내 | 상용 고도화는 별도 모듈로 표시 |

Public Core의 목적은 CGA 생태계를 넓히고, 누구나 기본 봇 시스템을 만들 수 있게 하는 것이다.

### 10.2 Commercial Modules

상용 가치가 큰 기능은 아래 3개 모듈로 분리한다.

| 모듈 | 역할 | 포함 후보 |
| --- | --- | --- |
| Advanced Builder Module | 좋은 봇을 빠르게 만들게 하는 고급 생성 자동화 | PDF Q&A 의도 생성 고도화, 의도 병합 추천, 중복 의도 감지, 답변 품질 점검, 프롬프트 템플릿 관리, 수동 LLM Handoff 결과 검증 |
| Operations Monitor Module | 운영 품질과 비용을 관리하는 상용 운영 기능 | 운영 대시보드 고도화, LLM 비용 집계, 채널 장애 알림, 미정의 질문 감지, 오분류 분석, 재학습 후보 추천, 운영 리포트 |
| License / Entitlement Module | 상용 기능 사용 권한 통제 | 라이선스 키 검증, 조직별 권한, 봇 수 제한, 채널 제한, 기능 활성화, 만료일 확인 |

### 10.3 모듈 분리 원칙

1. Public Core는 Commercial Module 없이도 실행 가능해야 한다.
2. Commercial Module이 없어도 기본 봇 생성, 답변 편집, 테스트, 기본 배포는 가능해야 한다.
3. Commercial Module은 플러그인 또는 별도 패키지 형태로 연결한다.
4. Commercial Module 부재 시 화면은 비활성 상태, 안내 상태, 또는 Basic 대체 기능을 보여준다.
5. Public Core가 Commercial Module 내부 구현에 직접 의존하면 안 된다.
6. 상용 모듈과 연결되는 인터페이스는 공개 가능하지만, 구현체는 별도 저장소 또는 별도 배포 패키지로 둔다.

### 10.4 화면 표시 원칙

CGA Studio 화면에서는 상용 모듈을 숨기지 않는다. 다만 공개 버전에서는 아래처럼 표시한다.

- Basic 기능: 바로 사용 가능
- Commercial 기능: `Commercial Module Required` 상태 표시
- 새 기능 가능 영역: `Approval Required` 상태 표시
- 라이선스 미확인: `Entitlement Not Connected` 상태 표시

이 방식은 사용자에게 제품 확장 방향을 보여주면서도 Public Core의 신뢰성을 유지한다.

### 10.5 승인 필요 항목

아래 항목은 구현 전 신산님 승인이 필요하다.

1. Public Core 라이선스를 AGPL-3.0, Apache-2.0, MIT 중 무엇으로 할지
2. Commercial Module을 별도 private repository로 둘지, 별도 package로 둘지
3. License / Entitlement Module을 로컬 검증 방식으로 둘지, 외부 라이선스 서버 방식으로 둘지
4. Advanced Builder Module의 1차 상용 기능 범위
5. Operations Monitor Module의 1차 상용 기능 범위

## 12. 1차 화면 디자인 판단 기준

좋은 CGA 화면은 아래 조건을 만족해야 한다.

1. 초보자가 다음에 무엇을 해야 하는지 바로 안다.
2. Aidot 기능명이 처음부터 과하게 노출되지 않는다.
3. 고급 사용자는 필요한 Aidot 기능으로 바로 들어갈 수 있다.
4. 현재 봇이 배포 가능한지 한눈에 보인다.
5. API/런타임/시뮬레이터/webchat 호환성이 깨지지 않는다.
6. 새 기능 없이 Aidot 기능 재배치만으로 설명된다.
7. 각 단계 화면은 신산님 승인 후에만 구현한다.

## 13. 1차 결론

CGA Studio는 Aidot를 새로 만드는 프로젝트가 아니다.

CGA Studio는 Aidot 기능과 운영 체계를 유지한 상태에서, 사용자의 봇 제작 흐름에 맞게 화면을 다시 구성하는 프로젝트다.

가장 먼저 확정해야 하는 것은 백엔드 기능이 아니라 화면 구조다.

1차 화면 시안은 사용자에게는 `01 봇 생성 -> 02 봇 구성 -> 03 상세 설정 -> 04 빌드 -> 05 테스트 -> 06 운영`으로 단순하게 보이고, 내부 기능 매핑은 `Create -> Setup -> Configure -> Review -> Edit -> Train -> Test -> Improve -> Deploy`로 관리한다.

## 14. 권한 기준 확정 기록

2026-06-12 기준 권한 운영 원칙은 아래와 같다.

### 14.1 그룹 / 역할 기본 원칙

- 모든 봇, API, 사용자 접근, 운영 권한은 그룹 기준으로 관리한다.
- 모든 컨텐츠는 기본적으로 동일 그룹 안에서만 공유한다.
- `System Admin Group`은 시스템 전체 관리를 위한 특수 그룹이다.
- `System Admin Group`에는 `system_admin` 역할만 둔다.
- `system_admin`은 모든 그룹과 모든 화면, 모든 기능에 접근할 수 있다.
- `group_admin`은 자기 그룹 안에서는 모든 작업을 할 수 있지만, 다른 그룹은 볼 수 없다.
- `builder`는 시스템 관리 기능을 제외한 봇 제작/운영 기능을 사용할 수 있고, 시스템 관리에서는 조회만 가능하다.
- `operator`는 봇 운영과 현황 조회만 가능하다.
- `reviewer`는 봇 제작, 봇 제작 워크플로우, 봇 운영, 현황 조회가 가능하다. 단, 봇 제작의 API 항목은 조회만 가능하다.
- `viewer`는 현황 조회만 가능하다.

### 14.2 API 답변 권한

- 봇 제작 영역의 API 답변 등록/수정/삭제는 `builder` 이상 권한에서만 가능하다.
- `reviewer`는 API 답변 화면을 볼 수 있지만 등록/수정/삭제는 할 수 없다.
- `operator`와 `viewer`는 API 답변 관리 화면의 수정 기능을 사용할 수 없다.

### 14.3 운영 중 조정 원칙

- 이 권한 기준은 1차 기준이며, 실제 화면 구현과 테스트를 진행하면서 신산님 확인 후 조정한다.
- Aidot의 봇/API/webchat 호환 구조는 변경하지 않고, CGA 화면과 권한 제어만 이 기준에 맞춘다.

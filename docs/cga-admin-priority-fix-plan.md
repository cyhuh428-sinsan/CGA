# CGA 관리자 영역 우선 수정 설계 계획서

작성일: 2026-06-23

## 1. 목적

- 현재 CGA는 Brity/Aidot 운영형 시스템 기준에서 관리자 영역이 아직 실사용 가능한 수준으로 정리되지 않았다.
- 이번 계획서는 `사용자관리`, `대화관리`, `시스템연계`, `기타관리`를 우선 복구 대상으로 정의하고, 그중 첫 착수 대상을 `기타 관리 > 템플릿 목록`으로 고정한다.
- 목표는 새 구조를 발명하는 것이 아니라, Aidot의 관리자 기능 구조와 API를 그대로 유지한 상태에서 CGA 화면과 동작을 정상화하는 것이다.

## 2. 절대 원칙

### 2.1 Aidot API 원형 유지

- Aidot API는 글자 하나라도 임의로 바꾸지 않는다.
- CGA는 Aidot API를 재설계하지 않는다.
- CGA 전용 관리자 API를 새로 만드는 방식은 금지한다.
- 가능하면 Aidot 원본 route, request, response, 필드명, 의미를 그대로 복사해 사용한다.

### 2.2 CGA 변경 허용 범위

- 변경 가능:
  - 화면 구성
  - 메뉴 구조
  - 노출 순서
  - 사용자 인터페이스
  - 안내 문구
  - 초보자/운영자 중심 UX
- 변경 금지:
  - Aidot 관리자 API 계약
  - 응답 구조
  - 데이터 의미
  - 권한 의미
  - 운영/동기화/이력 처리 방식

### 2.3 관리자 영역 우선 복구 원칙

- 챗봇 제작 기능보다 먼저 운영/관리 기능을 정상 동작시켜야 한다.
- 이유:
  - 운영형 시스템은 관리 화면이 먼저 살아 있어야 상태 확인, 동기화, 점검, 운영 검증이 가능하다.
  - 현재 CGA는 화면은 있으나, 관리 화면이 실제 Aidot 방식으로 동작하는지 불명확한 부분이 많다.

## 3. 우선 대상 범위

이번 우선 복구 범위는 아래 4개 메뉴 그룹이다.

### 3.1 사용자 관리

- 사용자 관리
- 로그인 이력
- 그룹 관리

### 3.2 대화 관리

- 공통 변수 관리하기
- 기본 메시지 관리

### 3.3 시스템 연계

- 채널 관리
- 봇스테이션 연계 현황

### 3.4 기타 관리

- 템플릿 목록

## 4. 왜 템플릿 목록부터 시작하는가

`기타 관리 > 템플릿 목록`을 첫 시작점으로 삼는 이유는 아래와 같다.

- 관리자 영역의 가장 전형적인 `목록 조회 -> 상세/수정 -> 저장` 패턴을 검증하기 좋다.
- Aidot 관리자 기능 중 UI 복잡도가 상대적으로 낮고, 공통 리스트/정렬/저장/권한 패턴을 먼저 고정하기 좋다.
- 템플릿 목록이 정상화되면 같은 패턴을 공통 변수, 기본 메시지, 채널 관리, 사용자 관리로 확장하기 쉽다.
- 즉 템플릿 목록은 단순 메뉴 하나가 아니라 `관리자 UI 공통 프레임의 기준 화면` 역할을 해야 한다.

## 5. 수정 목표 상태

각 관리자 메뉴는 최종적으로 아래 상태를 만족해야 한다.

- Aidot와 동일한 API 계약으로 데이터 조회 가능
- 목록이 실제 서버 데이터로 렌더됨
- 필터/정렬/검색이 Aidot 의미와 동일하게 동작
- 상세 조회 및 수정 저장이 실제 서버와 연결됨
- 권한 없는 작업은 차단됨
- 동기화 버튼이 있는 항목은 실제 동기화 동작 또는 동일 의미의 처리 결과를 보여줌
- 화면은 CGA 스타일이어도 동작 의미는 Aidot와 동일해야 함

## 6. 단계별 작업 계획

### Phase 1. 템플릿 목록 기준선 고정

목표:
- `기타 관리 > 템플릿 목록`을 첫 번째 정상 동작 기준 화면으로 복구한다.

작업 범위:
- Aidot 템플릿 목록 원본 화면/동작/API 확인
- CGA 템플릿 목록 화면의 현재 wiring 확인
- 목록, 상세, 저장, 삭제 가능 여부, 정렬 기준, 상태 표시 확인

완료 기준:
- 템플릿 목록이 Aidot 계약 그대로 실제 서버 데이터로 동작
- CGA에서 이 화면을 관리자 공통 패턴의 기준 구현으로 사용 가능

산출물:
- 템플릿 목록 기준 화면 정의
- 템플릿 목록 API 매핑표
- 공통 관리자 리스트 패턴 초안

### Phase 2. 관리자 공통 화면 패턴 확정

목표:
- 템플릿 목록을 바탕으로 관리자 공통 패턴을 정의한다.

공통 패턴 대상:
- 목록 조회
- 검색/필터
- 정렬
- 상태 표시
- 상세/수정 팝업 또는 패널
- 저장/삭제
- 권한 차단 메시지

중요:
- 이 단계는 API를 바꾸는 단계가 아니다.
- 화면 공통 shell만 정리하고, 데이터 의미는 Aidot 기준 그대로 유지한다.

완료 기준:
- 이후 사용자 관리, 공통 변수, 기본 메시지, 채널 관리에 그대로 적용 가능한 관리자 공통 UI 패턴 확정

### Phase 3. 사용자 관리 복구

대상:
- 사용자 관리
- 로그인 이력
- 그룹 관리

목표:
- Aidot 관리자 기준의 사용자/권한/그룹 관리 흐름을 CGA 화면에서 그대로 사용할 수 있게 한다.

핵심 확인:
- 목록 조회
- 그룹별/역할별 필터
- 로그인 이력 조회
- 그룹 생성/수정/삭제 가능 여부
- 권한 제약

완료 기준:
- 운영자가 CGA에서 사용자/그룹/로그인 이력을 실제 운영 확인 수준으로 사용할 수 있음

### Phase 4. 대화 관리 복구

대상:
- 공통 변수 관리하기
- 기본 메시지 관리

목표:
- 챗봇 런타임에서 실제 참조되는 공통 변수와 기본 메시지 관리 기능을 Aidot 의미 그대로 복구한다.

핵심 확인:
- 목록 조회
- 업로드/다운로드
- 수정/삭제
- 상태 사용 여부
- 다국어/범위/카테고리 의미

완료 기준:
- 운영자가 메시지/공통 변수 변경 후 그 반영 여부를 화면 기준으로 확인 가능

### Phase 5. 시스템 연계 복구

대상:
- 채널 관리
- 봇스테이션 연계 현황

목표:
- WebChat 포함 채널 운영과 외부 연계 상태를 Aidot 방식 그대로 관리 가능하게 한다.

핵심 확인:
- 채널 연결 정보 조회/수정
- 활성/비활성 상태 관리
- 봇스테이션 연계 현황 조회
- 운영 버전과 채널 노출 관계 확인

중요:
- 이 단계는 WebChat 호환성의 운영형 전제 조건이다.
- 채널/봇스테이션이 어긋나면 WebChat 연결 의미도 깨진다.

완료 기준:
- 운영자가 채널과 연계 상태를 실제 배포 점검 용도로 사용할 수 있음

### Phase 6. 관리자 영역 통합 검증

목표:
- 위 4개 메뉴 그룹이 서로 독립 화면이 아니라, 실제 운영형 시스템으로 이어지는지 검증한다.

검증 순서:
1. 템플릿 목록 조회/수정
2. 공통 변수/기본 메시지 변경
3. 사용자/그룹/로그인 이력 조회
4. 채널/봇스테이션 상태 확인
5. 관련 화면에서 반영 여부 확인

완료 기준:
- 관리자 화면이 단순 mock 화면이 아니라 운영 흐름의 일부로 동작함

## 7. 구현 기준

### 7.1 백엔드 기준

- Aidot 원본 API route를 최대한 그대로 사용
- CGA 서버는 Aidot API 응답 구조를 그대로 반환
- 기존 CGA mock/샘플 응답은 제거 대상
- 관리자 영역은 실제 서버 상태를 기준으로 동작해야 함

### 7.2 프론트 기준

- 메뉴 구조는 CGA 방식으로 유지 가능
- 단, 각 화면의 데이터/버튼/권한/상태 의미는 Aidot 그대로 유지
- 관리자 공통 리스트 화면 패턴을 만들되, 필드 의미를 일반화하거나 축약하지 않는다

### 7.3 문서 기준

- 각 단계 완료 시:
  - 기준 Aidot 화면
  - 사용 API
  - CGA 변경 범위
  - 변경 금지 범위
  - 검증 결과
  - 를 기록한다

## 8. 위험 요소

- 현재 CGA 일부 관리자 화면은 샘플 데이터/임시 구조에 기대고 있을 가능성이 높다.
- 기존 `CGA용 편의 구조`가 Aidot 원형 API와 충돌할 수 있다.
- 사용자 관리/그룹 관리와 같은 권한성 기능은 잘못 손대면 다른 메뉴 검증도 막힐 수 있다.
- 채널/봇스테이션은 운영 버전/WebChat 구조와 직접 연결되므로, 의미를 조금만 잘못 해석해도 전체 운영 모델이 틀어질 수 있다.

## 9. 이번 계획서의 우선순위

우선순위는 아래와 같이 고정한다.

1. `기타 관리 > 템플릿 목록`
2. 관리자 공통 화면 패턴 확정
3. `사용자 관리`
4. `대화 관리`
5. `시스템 연계`
6. 통합 운영 검증

## 10. 완료 정의

이번 설계 계획의 완료는 “문서 작성” 자체가 아니다.

아래 판단 기준이 준비되어야 완료로 본다.

- 어떤 메뉴부터 시작할지 확정됨
- 왜 템플릿 목록부터 시작하는지 설명 가능함
- Aidot API를 건드리면 안 되는 이유가 계획서에 반영됨
- 각 관리자 메뉴의 구현 순서와 완료 기준이 명확함
- 이후 실제 구현 시 단계별로 그대로 따라갈 수 있음

## 11. 최종 결론

현재 CGA는 관리자 영역이 실제 운영형 시스템 기준으로 아직 불완전하다.

따라서 이번 수정은 아래 원칙으로 시작해야 한다.

- Aidot API는 그대로 복사해 유지한다.
- CGA는 관리자 화면과 사용자 인터페이스만 재구성한다.
- 첫 착수는 `템플릿 목록`이다.
- 템플릿 목록을 관리자 공통 패턴 기준 화면으로 삼고, 그다음 `사용자 관리 -> 대화 관리 -> 시스템 연계` 순으로 확장한다.
